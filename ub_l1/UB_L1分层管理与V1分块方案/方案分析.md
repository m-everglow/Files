# UB/L1 分层管理与 V1 内部分块搬运方案

## 1. 目标与现状

目标：支持更大 tiling，同时保留 C1→V1→C2→V2 的有效流水重叠。

当前128×256用例中，C2→V2从双槽改为单槽后可编译、精度通过，但与128×128相比未看到性能提升。C1→V1单槽在完整lowering中新增64 KiB VF临时输出，仍然UB overflow。因此需要进一步缩小工作集，而不仅是减少核间槽位。

## 2. UB/L1统一管理能解决什么

这里的统一管理应理解为分层规划：决定数据放在哪一层、什么时候搬运、每次搬多少。UB和L1仍是不同的物理存储，容量不能直接相加作为VECTOR可任意访问的空间。

| UB紧张的原因 | L1中转的作用 |
|---|---|
| 提前load的数据长时间占UB等待使用 | 可将预取放到L1，临近使用再搬入UB，缩短UB生命周期 |
| 当前计算阶段的必需输入、输出、累加值和临时空间同时驻留UB已超限 | 若仍整块搬入UB，峰值问题不变，需要分块、融合或原地更新 |

例如，把GM→UB整块预取改为GM→L1整块预取→UB整块计算，只改变了等待位置，未必减少计算阶段的UB峰值。

## 3. 统一管理的潜在问题

- **瞬时工作集仍可能超限**：对给定计算粒度，必须同时驻留UB的数据仍需满足248 KiB限制。
- **L1也有容量限制**：需要同时容纳原有输入、核间双槽及新增暂存，不能默认L1总能接住UB溢出的数据。
- **增加搬运和同步**：新增L1→UB等传输，需要与已有FIX、VECTOR、MTE流水协调，可能产生新的等待。
- **生命周期跨核**：标量侧已经下发或更新SSBUF计数，不代表异步硬件访问已结束；复用前必须确认真实读写完成。
- **布局和切分要保持一致**：ND/NZ转换、对齐、stride及1C2V下两个AIV的行区间，都要随搬运路径一起处理。

因此，仅把UB中的alloc改成L1，或者增加一次整块中转，不能保证容量、正确性或性能。

## 4. 新想法：在V1内分行计算并搬到L1

保留宏观调度和核间双槽，只把V1产生softmax结果时使用的大临时UB改成可周转的小块。

    C1→V1：保持双槽
    V1：
        等待C1数据就绪、目标L1槽空闲
        for 每一组行：
            计算这些行的softmax结果
            写入小块UB
            搬到现有目标L1槽的对应位置
            安全复用小块UB
        发布完整L1结果就绪，允许C2消费
        释放C1→V1输入槽
    C2→V2：保持双槽

这是V1内部的分块循环，不是将整个V1及其调度逻辑重复执行。当前用例已有V1→C2的L1双槽，可继续使用这些完整结果的存放位置。

### 分块规则

1. **沿行分块，保留完整BN**：每行softmax的归约范围不变；不能把列直接切开后独立做softmax。
2. **临时UB在循环外分配**：循环内反复使用，不为每个分块保留独立buffer。
3. **每行状态只更新一次**：对应行的最大值、归约和发往V2的中间结果写入原有位置；后续V2接口保持一致。
4. **SSBUF计数按整个V1更新一次**：全部分片完成写入所需的数据同步后，再发布完整结果。C2仍按完整数据块消费。
5. **输入槽在最后一次读取完成后释放**：不能提前允许C1覆盖尚未消费的行。

### 容量估算：128×256

每个AIV处理64行。当前完整临时输出为%alloc_39，分配形状16×65×16×1、bf16，含padding占32.5 KiB。

| 方式 | 每AIV临时UB估算 |
|---|---:|
| 完整64行结果 | 32.5 KiB |
| 每块4行，沿用相同NZ组织和一行padding | 每槽约2.5 KiB |
| 两个4行临时槽 | 合计约5 KiB |
| 相比完整临时输出节省 | 约27.5 KiB |

该收益有望覆盖原始PlanMemory报告的25.25 KiB缺口，但不是已经验证的规划结果。实际大小取决于布局、对齐及lowering是否引入新buffer，必须重新统计。

### 内部流水

目标是让“小块A的搬运”和“小块B的计算”重叠。下一次复用A前，需要等待A的搬运读取结束；读取B前，需要确认其计算写入完成。初始可先用单个小块验证功能，再引入两个小块验证重叠。

4行分块意味着每个AIV的一次V1约有16块，搬运次数明显增加。块大小必须在临时UB容量、DMA效率、同步次数和VECTOR执行效率之间实测选择。分得越小不等于越快。

## 5. 能力边界

这一步主要缩小V1输出临时空间，尚未缩小完整QK输入双槽。它优先解决当前128×256的容量缺口。

若继续增大到BM=BN=256，每AIV的完整FP32 QK槽为128 KiB，双槽合计256 KiB，仅此就超过248 KiB。届时还需要让C1结果分片进入UB，由V1分片消费；同时检查L0C/L1容量和C1结果的驻留时间。

## 6. 验证顺序

1. 从原始双槽配置出发，只修改V1内部计算、搬运粒度。
2. 检查两AIV的行区间、NZ布局、尾块及同步；核对所有原始数据和状态均处理一次。
3. 重新lowering并统计真实before PlanMemory IR，确认临时空间缩小且未产生等量复制buffer。
4. 检查PlanMemory成功，再执行单次forward与torch参考精度比对。
5. 固定同一卡和输入，对比端到端、kernel耗时；再调分块大小和内部双缓冲。
