# VF1：按所有权分析 %130 的原地复用

**%130 是核间 buffer，不代表 V1 不能原地修改它。C1 必须等待反向 flag，V1 可以在归还之前使用这块空间。**

分析对象是原始 before_planmemory_attempt1.mlir，不是 L1 暂存版。代码已切回 qk-l1-ssbuf-staging；opt/compile 均已重新构建。

## 哪个输出能复用

| VF1 输出 | 当前 VF 内是否能直接写进 %130 | 原因 |
|---|---|---|
| %alloc_36，256 B | 不能 | 在开始读取 %130 之前就写入，会破坏未读输入 |
| %alloc_37，256 B | 不能 | 同样先写后读；结果还要通过 loop yield 留给后续迭代，不能随当前槽归还而丢失 |
| %alloc_38，256 B | **VF 内可以，调用处需推迟归还** | 每行输入读完后才写一个行和；可写入 %130 的前 256 B |
| %alloc_39，32.5 KiB | 当前顺序下不能同址 | NZ 写法会覆盖未读输入。第一段只读完 [0,256)，就会写 [2080,2112) |

%alloc_38 的具体复用方式：

- 把 %130 的前 256 B 当作 memref<64xf32>，作为 VF1 的 %arg5。
- 第 0 行的 256 个 f32 全读完，才写第 0 个行和。
- 后面 63 个行和也都写在原输入第一行的前 64 个 f32 位置。这一行已经读完，不影响后续行。
- 不改变数学计算、不改变 %alloc_39 布局，也不需要把 UB→L1 复制分块。

IR 中 %arg5 的旧值有一次读取，但 reduction 带 withoutInitMergeOp。VectorToHIVMAVE 在 enableTritonKernelCompile=true 时不将该初始值合入结果；分析按这条实际编译路径进行。

## 原调用处还差一次所有权调整

现有顺序：

    VF1 产生 %alloc_38
    发 V→FIX 反向 flag 2/5，允许 C1 再写当前槽
    将 %alloc_38 复制到 %alloc_14/15/16 中的一槽

若 %alloc_38 使用 %130 的空间，C1 可能先覆盖它，之后复制就读错了。因此不能只换输出地址。

合法顺序应为：

    VF1 把行和写入 %130 前 256 B
    将行和复制到选中的 %alloc_14/15/16
    该读取完成后，再发 V→FIX 反向 flag 2/5

其他小向量复制也可以一起放在归还之前。需要同步保证复制真正读完，而不仅是标量侧已下发。

**是否能复用，需要同时满足：写的是已经读完的输入；复用后的结果在归还 C1 前已经用完。**

## 当前 PlanMemory 有没有做到

**没有做到 %130 与 VF1 输出的这项复用。**

本次重放的 VF1 可复用表只列出 %alloc_36 可以使用 %alloc_18 / %alloc_35；未列出 %alloc_38 使用 %130。当前 VF 安全分析限制同一 block、相同 subview 迭代等条件，没有识别“内层读完整行、外层写行和”的已读前缀复用。

当前 PlanMemory 也没有按反向 flag 将核间槽细分为所有权区间。第一次 attempt 的记录：

| buffer | 地址（B） | 大小（B） | 分析中的存活区间 |
|---|---:|---:|---|
| %alloc_7 | 49920 | 65536 | 118–310 |
| %alloc_8 | 115456 | 65536 | 120–310 |
| %alloc_38 | 35072 | 256 | 204–241 |

地址不同，且 %alloc_38 的存活区间与两个槽重叠。重放仍报 UB 273.25 KiB / 248 KiB。上述时间是分析的操作编号，不是硬件时间。

这个机会按大小只省 256 B，不能单靠它解决 UB 超限。大的 %alloc_39 不能仅凭“V1 拥有 %130”就同址，仍要解决 VF 内部未读输入被覆盖的问题。
