# UB 内存规划重构方案：从 First-Fit 到冲突图着色

---

## 第一章 当前 First-Fit 方案的局限性：顺序敏感，结果由运气决定

### 1.1 现状回顾

当前核心寻址在 [SpecAlloc](file:///c:/Users/zhaojiqiao/Desktop/code/AscendNPU-IR-Dev/bishengir/lib/Dialect/HIVM/Transforms/PlanMemory.cpp#L2111-L2169)：`outline` 是一条从地址 0 开始的空闲/已用区间表，每个待放置的 `StorageEntry` 从低地址向高地址**顺序扫描**，找到第一个“跨度够大且与所覆盖区间的生命期不冲突”的位置即放置，然后 `UpdateOutline` 切洞、插入记录。这是教科书式的 **First-Fit over free-list**。

First-Fit 的每一步决策只看“**当前位置能不能放**”，完全不知道：

* 后面还有哪些 buffer 要来、它们多大、和谁冲突；
* 把这个 buffer 放在低地址的洞里，会不会堵死后面某个大 buffer 的唯一复用机会。

**放置顺序 = 分配质量**，而顺序本身没有被优化过。

### 1.2 代码自认：用 20 次随机重试“赌”一个可行解

[PlanMemoryForFuncOp](file:///c:/Users/zhaojiqiao/Desktop/code/AscendNPU-IR-Dev/bishengir/lib/Dialect/HIVM/Transforms/PlanMemory.cpp#L2986-L3028) 的重试循环是最直接的证据：

```cpp
constexpr int kPlanRetryCount = 20;
// The current plan-memory algorithm is sensitive to the order in which some
// candidate buffers are considered. We retry planning with different
// deterministic shuffle seeds to improve the chance of finding a valid plan
// without making the pass behavior non-reproducible.
// TODO: Remove the retry loop once the plan-memory algorithm is improved to
// produce a stable valid plan in a single attempt.
for (int attempt = 0; attempt < kPlanRetryCount; ++attempt) {
  MemLivenessAnalysis memLiveness(funcOp, this->memMode,
                                  ..., /*randomSeed=*/attempt);
  ...
}
```

注意 `randomSeed=attempt` 传给了 **MemLivenessAnalysis**——也就是说每次重试连候选 buffer 的**枚举顺序**都被换了一次。这等于官方承认：算法本身不保证成功，靠换顺序碰运气，20 次全失败才报 `PLAN_FAILED`。

此外 [GetReorderRootStorageEntry](file:///c:/Users/zhaojiqiao/Desktop/code/AscendNPU-IR-Dev/bishengir/lib/Dialect/HIVM/Transforms/PlanMemory.cpp#L1968) 手工把 DMA buffer 排到队列前面优先分配——这是又一层人工排序补丁，试图缓解（但并未消除）顺序敏感性。

### 1.3 反例演算：同一实例，顺序不同，峰值差 67%

设 UB 预算 8KB，三个 buffer：


| Buffer | 生命期   | 大小 |
| ------ | -------- | ---- |
| A      | \[0, 4]  | 4KB  |
| B      | \[5, 10] | 4KB  |
| C      | \[2, 8]  | 2KB  |

冲突关系（生命期相交即不能共享地址）：A—C（\[0,4]∩\[2,8]≠∅）、B—C（\[5,10]∩\[2,8]≠∅）、A—B **无冲突**。

**顺序一 \[A, B, C]**（好运）：

    Step1: A@0-4                        地址线: [A####|--------]
    Step2: B 生命期与A不相交 → 复用0-4    B@0-4   [A/B###|--------]
    Step3: C 与A、B都冲突 → 放在4-6       C@4-6   [A/B###|CC|----]
    峰值 = 6KB ✓

**顺序二 \[C, A, B]**（厄运）：

    Step1: C@0-2                        地址线: [CC|----------]
    Step2: A 与C冲突(2-4重叠) → A@2-6    [CC|AAAA|----]
    Step3: B 与C冲突(5-8重叠)，低地址放不下
           → B@6-10                      [CC|AAAA|BBBB]
    峰值 = 10KB ✗ 超出8KB预算

区别在哪？顺序二里 C 这个**小 buffer 先占据了地址 0**，把地址线低段切出一个 2KB 的洞。A（4KB）塞不进洞只能上推；等 B 来的时候，唯一能复用的低地址区域已经被 C 的生命期“污染”——B 与 C 在 \[5,8] 重叠，无法共享。**C 抢占了它不配拥有的黄金低地址**，而 First-Fit 对此毫无知觉，因为它从不评估“C 放这里对后续的影响”。

### 1.4 顺序敏感的三个衍生代价

1. **结果质量是种子彩票**。种子固定保证了单次编译可复现，但任何无关改动（上游 pass 多了一个 op、buffer 枚举顺序漂移）都会改变哪次 attempt 碰上好运，UB 峰值随之波动，性能回归测试基线脆弱、难归因。
2. **编译性能浪费**。最坏情况 20 次完整的“建活跃性分析 → 建图 → 规划”，每次都是 O(n²) 级，20 倍的重复劳动换一个本可以一次求出的解。
3. **失败诊断困难**。20 次失败后报 `PLAN_FAILED`，开发者无法区分：是这个 kernel 的 UB 需求真的超了（实例不可行），还是 20 个顺序都不巧（算法运气差）。两种情况混在同一个报错里。

### 1.5 小结

First-Fit 的本质缺陷是**局部贪心没有全局视野**：冲突关系（谁能和谁共享地址）是实例的**全局图结构信息**，但 First-Fit 把它降格为扫描过程中的逐点试探，让“谁先来”决定了“谁能复用谁”。下一章把这同一个冲突关系显式建成图，用全局着色求解——顺序的影响将被彻底消除。

## 第二章 图着色全局分配算法设计

### 2.1 问题建模：UB 冲突图（UDG）

**节点**：预处理后的 `StorageEntry`（沿用现有 `MergeInplaceSE` / `ExpandMultiBufferStorageEntry` 产物，不重造）。

**节点权重**：`w(v) = AlignUp(constBits, align)`，即对齐后大小。

**边**：两节点不能共享地址槽的所有情况，全部来自现有分析：


| 边类型    | 判定                                                           | 替代的现有代码                |
| --------- | -------------------------------------------------------------- | ----------------------------- |
| E\_life   | 生命期区间相交：`[a.alloc, a.free] ∩ [b.alloc, b.free] ≠ ∅` | `VerifyConflictStage0`        |
| E\_unique | 任一方`memoryUnique` 且不在 `cvMixIdReuseAllowedPairs` 白名单  | `GetOverlapBufferLife` 内特判 |

**目标**：把节点划分为若干**独立集**（同一独立集内的节点两两无边，可共享一个地址槽）。每个槽的宽度 = 槽内最大节点权重。最小化：

    UB峰值 = Σ(各槽宽度)

这就是**加权图着色**：颜色 = 地址槽。与经典着色最小化颜色数不同，这里最小化的是“权重加权的颜色成本”，但求解框架完全一致。

### 2.2 算法总体流程

    BCIC(StorageEntryVec, ubSpaceSize, align):
      Phase 0  建图        BuildUDG(): O(n²) 两两判生命期相交（按时间排序可加速）
      Phase 1  下界计算    sweep-line 扫掠求峰值下界 LB
                            若 LB > ubSpaceSize → 直接报"实例不可行"（非运气问题）
      Phase 2  节点排序    动态优先级队列（DSATUR 变体，见 2.4）
      Phase 3  槽位分配    逐节点评估全部候选槽，选"对全局峰值增量最小"的槽
      Phase 4  地址生成    槽做前缀和得到 offset，回填 buffer2Offsets

### 2.3 Phase 1：sweep-line 下界——先知道“最好能多好”

把每个节点的生命期 `[alloc, free]` 转成两个事件：`(alloc, +w)` 和 `(free+1, -w)`，按时间排序后做前缀和，最大值即下界：

```cpp
uint64_t ComputeLowerBound() {
  // 峰值 ≥ 任意时刻同时活跃节点的权重之和（它们两两生命期相交，必然两两异槽）
  // LB = max over t of Σ{w(v) : v 活跃于 t}
}
```

这个 LB 是**硬下界**：t 时刻活跃的所有节点两两有 E\_life 边，构成团，必须各占一个槽，权重之和是逃不掉的。有了它，任何分配结果都可以立刻量化差距：`结果峰值 - LB = 启发式损失`。

### 2.4 Phase 2：DSATUR 动态排序——系统化取代随机 shuffle

不预先定死顺序，而是每放一个节点后动态选下一个：

    priority(v) = w(v) × saturation(v)
    saturation(v) = v 的已放置邻居所占的不同槽位数 + 1

直觉：

* **w(v) 大**的先放——大 buffer 是稀缺资源，晚放就只剩烂槽（对应第一章反例里“小 C 抢占低地址”的失败模式，反转它）；
* **saturation 高**的先放——邻居已经把路堵得差不多的节点，自由度最小，再拖就没得选（DSATUR 的经典思想）。

这把现有代码里两处手工排序（`GetReorderRootStorageEntry` 的 DMA 优先、20 次 shuffle）统一成一个确定性原则：**大者先、被夹死者先**。

### 2.5 Phase 3：槽位分配——每步评估全局增量，而非“取第一个”

对当前节点 v，候选方案有三类，逐一计算**峰值增量 Δpeak**：


| 候选         | 条件                  | Δpeak                    |
| ------------ | --------------------- | ------------------------- |
| 放入现有槽 s | v 与 s 内所有节点无边 | `max(0, w(v) − s.width)` |
| 扩槽放入 s   | 同上（v 比槽宽）      | `w(v) − s.width`         |
| 开新槽       | —                    | `w(v)`                    |

**选 Δpeak 最小者**；平手时选 Best-Fit（剩余空间最小，保住大洞）。对比 First-Fit 的“从地址 0 扫到第一个能放的洞”——这是每步决策质量的本质差别。

### 2.6 完整示例演算一：第一章反例的消解

A/B/C（预算 8KB：A\[0,4]/4KB，B\[5,10]/4KB，C\[2,8]/2KB；边 A—C、B—C）。

**Phase 1 下界**：事件扫掠：

    t=0: +4 (A)        → 峰 4
    t=2: +2 (C)        → 峰 6   ← {A,C} 同时活跃
    t=4: -4 (A)        → 峰 2
    t=5: +4 (B)        → 峰 6   ← {B,C} 同时活跃
    t=8: -2 (C), t=10: -4 (B)
    LB = 6KB ≤ 8KB → 可行，进入着色。

**Phase 2/3 着色**（初始 saturation 全为 1）：

    贪心思路：占用越大优先级越高， 图边越多优先级越高 saturation=space*edagenum
    优先级: A = 4×1 = 4, B = 4×1 = 4, C = 2×2 = 4 → 先放 A（大者先）
    A → 无邻居已放 → 开槽 S1，Δpeak=4。S1={A}, width=4
    更新: C 的 saturation=4 → C 优先级=2×1=2；B saturation=4 → 0。平手取饱和度高者 C
    B → 邻居 A 占 S1，S1 不可进 → 开槽 S2，Δpeak=2。S2={C}, width=2
    C→ 邻居只有 C(占S2)；S1 内无 B 的邻居 → 放入 S1，Δpeak=0 ✓

**Phase 4 地址生成**：

    S1.width=4 → offset 0；S2.width=2 → offset 4
    地址:  0        4      6
| S1:A,B | S2:C |
    峰值 = 4 + 2 = 6KB = LB，最优解。

**关键观察**：换成任何输入顺序 \[C,A,B]、\[B,C,A]……DSATUR 的动态排序都会先放 A 或 B（权重大），C 永远不会抢占低地址大槽。**结果与顺序无关，且恰好命中理论下界。** 20 次重试循环可整体删除。

### 2.7 完整示例演算二：五个 buffer，展示 DSATUR 与 Δpeak 决策的细节

UB 预算 10KB，五个 buffer：


| Buffer | 生命期    | 大小 |
| ------ | --------- | ---- |
| P      | \[0, 3]   | 3KB  |
| Q      | \[2, 6]   | 2KB  |
| R      | \[4, 9]   | 3KB  |
| S      | \[7, 12]  | 2KB  |
| T      | \[10, 14] | 3KB  |

**建图**（生命期相交即有边）：P—Q（\[0,3]∩\[2,6]）、Q—R（\[2,6]∩\[4,9]）、R—S（\[4,9]∩\[7,12]）、S—T（\[7,12]∩\[10,14]）；P—R、P—S、P—T、Q—S、Q—T、R—T 均无交。**图是一条链：P—Q—R—S—T**。

**Phase 1 下界**：

    t=2: {P,Q}=5   t=4: {Q,R}=5   t=7: {R,S}=5   t=10: {S,T}=5
    LB = 5KB ≤ 10KB → 可行。

**着色过程**：

    Step 0  优先级: P=3×1, Q=2×2, R=3×2, S=2×2, T=3×1
            R 优先级最高(6) → R 先放
            R → 开槽 S1，Δpeak=3。S1={R} w=3

    Step 1  Q: w=2, sat=1 (邻居R在S1) → 优先级 2×2=4
            S: w=2, sat=1 → 4；P: 3×1=3；T: 3×1=3
            平手 Q/S，取先入队的 Q
            Q → 邻居 R 占 S1 → 只能开新槽 S2，Δpeak=2。S2={Q} w=2

    Step 2  S: sat=1 → 4；P: sat=1(R?否，P的邻居是Q，Q在S2) → 3×2=6！P 最高
            P → 邻居 Q 占 S2；S1 内无 P 的邻居(R与P无边) → 放入 S1，Δpeak=0 ✓
            S1={R,P} w=3（P=3 恰好装满）

    Step 3  S: sat=1(R在S1) → 2×2=4；T: sat=1 → 3×1=3 → S 先
            S → 邻居 R 占 S1、T 未放；S2 内无 S 的邻居(Q—S无边) → 放入 S2，Δpeak=0 ✓
            S2={Q,S} w=2

    Step 4  T → 邻居 S 占 S2；S1 内无 T 的邻居(R—T无边) → 放入 S1，Δpeak=0 ✓
            S1={R,P,T} w=3

**Phase 4**：

    S1 w=3 → offset 0；S2 w=2 → offset 3
    地址:  0         3     5
| S1:P,R,T| S2:Q,S |
    峰值 = 3 + 2 = 5KB = LB，链图完美二分，最优。

**对照组：First-Fit 按输入顺序 \[P,Q,R,S,T]**：

    P@0-3 → Q: 与P冲突 → Q@3-5 → R: 与Q冲突 → R@5-8
    → S: 与R冲突 → S@8-10 → T: 与S冲突 → T@10-13
    峰值 = 13KB ✗（First-Fit 在链图上退化成"全不相邻堆叠"）

5KB vs 13KB，**差 2.6 倍**。原因：First-Fit 只做逐点生命期判定，永远发现不了“P/R/T 生命期两两不相交、可以叠进同一个 3KB 槽”这个全局结构；着色在 Step 0 就从图上看到了。

### 2.8 工程落地要点

**保留不动**：`MemLivenessAnalysis`、`GenerateStorageEntry`、`MergeInplaceSE`、`ExpandMultiBufferStorageEntry`、scope 分离、`BuildCVReuseAllowedPairs`、`id2Offsets` 双核同步、两遍执行流与 RewritePattern 写回。

**删除**：`SpecAlloc` 扫描循环、`outline`/`history`/`PlanRecord`、回滚全套、`PlanMemoryForFuncOp` 的 20 次重试循环、`GetReorderRootStorageEntry` 手工排序（被 DSATUR 取代）。

**新增**：`UBColorizer` 类，四个方法对应四个 Phase，约 400 行。

**灰度**：加 `--use-ub-coloring` 开关默认关闭；对既有测试集断言 `colored_peak ≤ first_fit_peak` 作为验收指标。

**复杂度**：建图 O(n²)（可按时间排序优化）、着色 O(n·k)，**单次执行**，无重试。
