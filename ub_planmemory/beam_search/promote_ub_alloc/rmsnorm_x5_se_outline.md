# RMSNorm x5-weight5：stable/current 的 SE 与 outline

本文直接使用 **PlanMemory 输出 IR 的 SSA 名称**，不另外给 buffer 起代号。

- `R`：`scf.for %arg16` 的作用域。
- `A`：R 内第一个、带 iter_args 的 `%arg17` 循环。
- `B`：R 内第二个 `%arg17` 循环。

例如 `A.%24` 就是循环 A 内的 `%24`，`B.%24` 是循环 B 内另外一个 `%24`。前缀仅用于区分 IR 作用域。`A.%24（槽0）`、`A.%24（槽1）` 表示该 pointer_cast 的两个 MultiBuffer 地址对应的 SE，不是两个不同 SSA value。

原始 IR：[stable](/home/m00953828/mojo/mojo_data/rmsnorm_x5_planmemory_analysis_20261013/stable/planmemory_after_3.mlir:139)、[current](/home/m00953828/mojo/mojo_data/rmsnorm_x5_planmemory_analysis_20261013/current/planmemory_after_3.mlir:139)。两版下列 op 的行号相同。

## 先看一条线：哪些 buffer 复用，有没有碎片

按低地址到高地址排列，大小单位为 B，图的宽度不按比例。`/` 表示两个 buffer 在不同生命期使用同一组地址。

```text
stable：
0 ──[A.%24 / B.%24：81920B]──[R.%10：64B]──[B.%26：81920B]──[B.%25：81920B]──[其余标量：128B]──[空闲：8000B]── 253952

current：
0 ──[A.%24 / B.%26：81920B]──[B.%25：81920B]──[B.%24：81920B]──[全部标量：192B]──[空闲：8000B]── 253952
```

- **`A.%24`**：L173 `hivm.hir.load` 的 UB 目标，经 subview/collapse_shape 访问。
- **`B.%26`**：L213 `hivm.hir.load` 的 UB 目标，经 subview 访问。
- **`B.%25`**：L221 另一条 `hivm.hir.load` 的 UB 目标。
- **`B.%24`**：L222 VF 调用的第 5 个参数，被 VF 写入；L227 `hivm.hir.store` 的 UB 源。
- **`R.%10`**：L180 fused VF 调用的第 4 个参数；L185 标量 store、L187 memref.load 的源。

每个 81920 B 方框内部有两个 40960 B 槽位。stable 复用的是 `A.%24` 与 `B.%24`；current 复用的是 `A.%24` 与 `B.%26`。

**两版最终都没有中间空闲洞，8000 B 空闲空间集中在尾部。** stable 中的 `R.%10` 虽然夹在大块之间，但它占用的 64 B 已被使用，不是空闲碎片。单槽 f32 标量由 4 B 对齐为 32 B；两版都有相同的 6 个小 SE，对齐填充相同。

stable 的“其余标量”按地址顺序为 `A.%36 → R.%6 → R.%7 → R.%4（与 A.%37 alias）`；current 的“全部标量”为 `R.%10 两槽 → R.%6 → R.%7 → R.%4（与 A.%37 alias）→ A.%36`。

## 1. 输入 SE：两版相同

以下生命期编号是 liveness 的线性操作编号，不是时间单位，也不是 DMA 实际完成时间。

| 对应的 IR buffer | op/用途 | 每槽原始大小 B | 每槽规划大小 B | SE 数 | bufferLife |
|---|---|---:|---:|---:|---|
| `A.%24` | L173 load 目标；L175 VF 调用第 1 参数 | 40960 | 40960 | 2 | `[49,58]` |
| `B.%26` | L213 load 目标；L222 VF 调用第 1 参数 | 40960 | 40960 | 2 | `[89,109]` |
| `B.%25` | L221 load 目标；L222 VF 调用第 2 参数 | 40960 | 40960 | 2 | `[101,109]` |
| `B.%24` | L222 VF 调用第 5 参数；L227 store 源 | 40960 | 40960 | 2 | `[109,114]` |
| `R.%10` | fused VF 的标量结果，供 store/load 使用 | 4 | 32 | 2 | `[65,72]` |
| `R.%6` | `memref.store %5, %6` 的目标 | 4 | 32 | 1 | `[15,121]` |
| `R.%7` | `memref.store %arg10, %7` 的目标 | 4 | 32 | 1 | `[17,121]` |
| `R.%4 ≡ A.%37` | 必需 alias：输入中 `%alloc` 与 `%alloc_10` 合并 | 4 | 32 | 1 | `[19,121]` |
| `A.%36` | L175 VF 第 2 参数与 L177 VF 第 2 参数 | 4 | 32 | 1 | `[58,60]` |

```text
SE 集合（还没有表达分配顺序）
├─ A.%24             槽0、槽1：2 × 40960 B
├─ B.%26             槽0、槽1：2 × 40960 B
├─ B.%25             槽0、槽1：2 × 40960 B
├─ B.%24             槽0、槽1：2 × 40960 B
├─ R.%10             槽0、槽1：2 ×    32 B
├─ R.%6                            32 B
├─ R.%7                            32 B
├─ R.%4 ≡ A.%37                    32 B（两个 alias value，一个 SE）
└─ A.%36                           32 B
```

合计 9 组逻辑 buffer，展开后为 **14 个 SE：8 个大 SE、6 个小 SE**。UB 的 scope root 是其中一个真实 SE，另外 13 个通过 mergedChildren 参与分配；9 组不是 9 个 UB root。current 将这 9 组用作 DSATUR group。

本例 `optionalInplaceEdges=0`。上图中的大 buffer 同址属于后续地址复用，不是 optional inplace 把两个大 buffer 合并成一个 SE。

不复用时需要 `8×40960 + 6×32 = 327872 B`；本例 UB 容量为 `2031616 bit / 8 = 253952 B`，因此必须复用部分地址。

## 2. 进入 first-fit 的顺序：两版不同

### stable：按类别排队，不比较全局冲突压力

`GetReorderRootStorageEntry` 取出 `root + mergedChildren`，按下面的类别拼接，再把同一 MultiBuffer 的槽0、槽1放在一起：

```text
memoryUnique → DMA touched → 普通 → scalar pipeline
```

本例没有 memoryUnique；各类的顺序为：

| 类别 | 本例 buffer 的顺序 |
|---|---|
| DMA touched | `A.%24 → R.%10 → B.%26 → B.%25 → B.%24` |
| 普通 | `A.%36` |
| scalar pipeline | `R.%6 → R.%7 → R.%4 ≡ A.%37` |

本例使用默认策略，**同类保留进入分类时的先后顺序**，不按大小或冲突图重新选择。因此 `R.%10` 虽然只有两槽共64 B，但属于 DMA 类，仍夹在几个81920 B大组之间。代码只有显式启用 `LARGEST_FIRST` 时才会在类内按大小排序；本例不是该路径。

### current：把同一 MultiBuffer 组成 group，再用 DSATUR 选顺序

`BuildDSaturStorageEntryOrder` 先按大小、生命周期起止、op位置等规范化节点，给节点稳定编号；再把14个SE组成9个group。**规范化顺序只是稳定编号的依据，不是最终分配顺序。**

接着建立包含生命周期及流水线冲突的group图，每轮选一个group、着色，再更新剩余group的saturation。主要比较顺序为：

```text
saturation 大 → 冲突容量大 → group容量大 → optional收益大
→ 可复用group数少 → liveTicks长 → pipeline优先级高 → degree大 → 稳定ID小
```

**本例9个group在这个保守冲突图中两两相连，degree均为8。** 因而第1轮各候选saturation都是0，第2轮都是1，后面依次增加；saturation没有区分候选。图中还包含DMA等流水线约束，不代表降到较低spec level后这些buffer也绝对不能复用。另因 `optionalInplaceEdges=0`，两项optional收益均为0，本例也不参与裁决。

真正决定顺序的是下面几项，数值来自现有 `[DSATUR-Score]` 日志，容量由bit换算为B：

| group（按最终选择顺序） | group容量 B | 冲突容量 B | 可复用group数 | liveTicks |
|---|---:|---:|---:|---:|
| `B.%26` | 81920 | 245952 | 3 | 21 |
| `B.%25` | 81920 | 245952 | 3 | 9 |
| `B.%24` | 81920 | 245952 | 3 | 6 |
| `A.%24` | 81920 | 245952 | 4 | 10 |
| `R.%10` | 64 | 384 | 5 | 8 |
| `R.%6` | 32 | 256 | 0 | 107 |
| `R.%7` | 32 | 256 | 0 | 105 |
| `R.%4 ≡ A.%37` | 32 | 256 | 0 | 103 |
| `A.%36` | 32 | 256 | 4 | 3 |

这里“冲突容量”是 `Σ min(本group容量, 冲突邻居容量)`；“可复用group数”只统计**生命周期不冲突**的group，不包括流水线限制，因此与全连接冲突图并不矛盾。`liveTicks` 是生命周期区间长度，不是执行时间。

选择过程直接看这几步即可：

1. 四个大group冲突容量相同、大小相同。`B.%26 / B.%25 / B.%24` 的可复用group数为3，少于 `A.%24` 的4，所以先选B的三个。
2. B的三个之间由生命周期长度裁决：`21 > 9 > 6`，因此是 `B.%26 → B.%25 → B.%24`，随后才是 `A.%24`。
3. 大group处理完，`R.%10` 的冲突容量384 B高于其他小group的256 B，所以先选它。
4. 剩余小group中，`R.%6 / R.%7 / R.%4` 的可复用group数为0，少于 `A.%36` 的4，因此先处理这三个；它们再按 `107 > 105 > 103` 排序，最后处理 `A.%36`。

最后把选出的group展开为槽0、槽1，安装回 `root + mergedChildren`，交给原有first-fit / MultiSpec；graph路径跳过旧的分类重排，避免覆盖DSATUR顺序。

**所以，本例变化不是SE集合变了，而是旧的“类别+原先后顺序”变成了“冲突压力+复用稀缺程度+生命期”的排序。最关键的变化是 `B.%26` 替代 `A.%24` 成为第一个分配的大group。**

### 两版最终顺序及对复用对象的影响

每个双槽 buffer 内部都是先槽0、后槽1。下面展示最后成功的多档规划顺序：

```text
stable：
A.%24 两槽 → R.%10 两槽 → B.%26 两槽 → B.%25 两槽 → B.%24 两槽
          → A.%36 → R.%6 → R.%7 → R.%4（与 A.%37 alias）

current：
B.%26 两槽 → B.%25 两槽 → B.%24 两槽 → A.%24 两槽 → R.%10 两槽
          → R.%6 → R.%7 → R.%4（与 A.%37 alias）→ A.%36
```

current 的 DSATUR 先选 `B.%26、B.%25、B.%24、A.%24` 四个大 group，然后处理小 group。first-fit 和 MultiSpec 仍按各自规则执行；DSATUR 颜色不是物理地址编号。

stable 先放 `A.%24` 两槽到 0/40960，后来 `B.%24` 两槽降到 spec level 2，复用这两段地址。current 先放 `B.%26` 两槽到 0/40960，后来 `A.%24` 两槽在 level 3 失败、降到 level 2，复用这两段地址。

两版此前都试过无限大 outline 的 no-stall 单档规划，需求超过 UB 容量；以下只展示随后受容量约束的成功多档规划。

## 3. outline 是怎样的结构

`MemBoundList` 是按地址从低到高连接的 `MemoryBound` 链表，每个节点记录：

```text
outline → bound → bound → … → bound
           ├─ offset、extent：地址区间 [offset,offset+extent)
           ├─ bufferLifeVec：曾放入此区间的累计生命周期
           └─ lastStorageEntry：最后被规划进来的 SE
```

初始只有一个空节点 `[0,253952)`。放入 SE 时，`splitOutline=true` 把占用部分与剩余尾部切开；复用已有节点时，把新生命期并入旧生命期，并更新 last。

`lastStorageEntry` 反映**规划顺序**，不是 IR 执行顺序。代码内部地址单位是 bit，本文件全部换算成 B。历史日志没有直接打印最终链表，下表由成功分配日志和 UpdateOutline 的分段更新规则恢复；其中“使用者”是解释用列，不是 MemoryBound 新增字段。

## 6. 具体看一次切分和一次复用

current 先放 `B.%26（槽0）`，从初始空节点切出 40960 B：

```text
放置前：
[0,253952)       life={}                         last=null

放置后：
[0,40960)        life={[89,109]}                 last=B.%26（槽0）
[40960,253952)   life={}                         last=null
```

后来放 `A.%24（槽0）`，它在 level 2 复用大小相同的 `[0,40960)`。这一次没有需要切分的尾部：

```text
复用前：
[0,40960)        life={[89,109]}                 last=B.%26（槽0）

复用后：
[0,40960)        life={[49,58],[89,109]}          last=A.%24（槽0）
```

旧生命期没有被丢弃，也没有被扩成连续的 `[49,109]`；中间的时间空隙仍保留。

current 再放 `R.%10（槽0）` 时，才从未用尾部切出 32 B：

```text
放置前：
[245760,253952)  life={}                         last=null

放置后：
[245760,245792)  life={[65,72]}                  last=R.%10（槽0）
[245792,253952)  life={}                         last=null
```

stable 对 `B.%24（槽0）` 的复用也是同样的等大更新，只是旧生命期来自 `A.%24`，新生命期来自 `B.%24`。

## 7. 两版结果的区别

两版都得到 13 个 bound：6 个 40960 B 大节点、6 个 32 B 小节点、1 个 8000 B 空尾。占用都为 245952 B，比不复用的 327872 B 少 81920 B。

性能相关的区别是低地址的复用对象：stable 的 `B.%24` 被 B 的 `hivm.hir.store` 读取；current 的 `B.%26` 被 L222 的 VF 调用读取。后续同步因此从等待 MTE3 读取完成，变成相应位置等待 V 读取完成。静态 bufferLife 不重叠，不代表异步 DMA 已执行完成；真实 wait/set 变化见 [IR 地址与同步图解](rmsnorm_x5_planmemory_ir_changes.md)。

## 复用的差异

**涉及的 buffer 和流水线组合不同，但 level 3 拒绝复用的代码规则相同。**

| 版本 | 尝试复用的两个 buffer | DMA 类型 |
|---|---|---|
| stable  | `A.%24` 与 `B.%24` | load 目标 MTE2 ↔ store 源 MTE3 |
| current | `A.%24` 与 `B.%26` | load 目标 MTE2 ↔ load 目标 MTE2 |

`BufferPipeConflict` 的判定比较保守：**只要涉及 DMA buffer，就返回冲突**，并不只禁止 MTE2/MTE3 之间复用；MTE2/MTE2 也会被禁止。

两版降到 level 2 后，这两个 buffer 分属不同父循环，因此可以复用。

真正不同的是复用后的依赖：stable 要保护 `store` 对 UB 的读取；current 要保护 VF 对 load 结果的读取，后续插入的同步因此不同。

## 潜在收益来源

从当前代码看，**DSATUR 最适合“必须复用内存，而且不同 buffer 的分配难度差异明显”的 IR**。它的优势是根据全体 SE 的约束选顺序，比旧的分类排序掌握更多信息。

首先有个明确的生效前提：只有 `requiredSize > maxBits` 才执行 DSATUR；容量足够直接走 `PlanBuffersWithoutReuse`，排序不会带来收益。见 [排序入口](/home/m00953828/AscendNPU-IR/bishengir/lib/Dialect/HIVM/Transforms/regbase/PlanMemory.cpp:2138)。

| 适用场景 | 代码依据 | 可能改善什么 |
|---|---|---|
| **冲突关系复杂，少数 buffer 特别难放** | `saturation` 优先，其次比较 `weightedConflictBytes` | 先安排受限制较多的 group，减少它被其他分配挤到无处可放的情况 |
| **大、小 buffer 混合，且冲突容量差异大** | `Σ min(自身容量, 邻居容量)`，再比较 group 总大小 | 优先处理容量压力大的 group，避免小块过早影响大块布局 |
| **MultiBuffer 的槽数、单槽大小差异大** | 将相关槽位组成 group，`weight` 是所有槽位容量之和 | 识别整个 MultiBuffer 组的容量压力；旧排序主要看单个 SE 的大小 |
| **大小接近，但复用机会、生命期差异大** | 后续比较 `reuseCandidateCount`、`liveTicks` | 在前面评分相同时，优先安排复用机会少、生命期长的 group |
| **旧分类优先级与实际分配难度不一致** | 新排序中 `pipelineRank` 是较后的裁决项；旧排序先固定 DMA/普通/scalar 类别 | 大而难放的普通 buffer 可以先于小而灵活的 DMA buffer |

其中 MultiBuffer 的改进**不是“让槽位连续分配”**——旧代码已经做了这一点。新增价值是按**整组容量及整组冲突**选择优先级。

也能从代码看出几个收益有限的场景：

- **冲突图接近完全图**：例如很多 DMA buffer 在 level 3 下两两冲突，saturation 很难区分节点，主要靠容量等后续评分排序。
- **大小、生命期和约束都相近**：新旧顺序可能差别不大。
- **真实容量需求已经不可满足**：换顺序无法消除必须同时存在的 buffer。
- **group 数极大**：构图和动态排序有额外编译开销，需要确认是否被减少的重试抵消。

因此，代码层面应优先筛选：**UB 必须复用、group 容量差异大、冲突压力不均匀、MultiBuffer 组复杂**的 IR，验证分配成功率和回退次数。

至于运行性能，当前评分没有直接计算同步等待代价、MTE2/MTE3 重叠或实际耗时。**同步改善可能出现，但不能仅凭这份代码保证性能更好，也不能保证结果始终不差于 legacy。**
