# 三个典型用例对比（2026-10-19）

源码版本：`3493d4f426f3`；设备：Ascend950PR_9579，卡 6。两版固定相同 Triton 配置、独立缓存，性能各测两轮，每轮每个 kernel 取 10 条样本均值。以下输出和梯度检查均通过。

## 1. 门控 LayerNorm backward：stable 九次规划均溢出，current 第一档通过

Kernel：`layer_norm_gated_bwd_kernel1`。输入 `4096×768`、FP32；`BT=4, BD=1024, num_warps=4, multibuffer=True`。

Before PlanMemory IR：[layer_norm_gated_bwd_kernel1.before_planmemory.mlir](/home/m00953828/Files/ub_planmemory/Q3_triton_kernel/layer_norm_gated_bwd_kernel1.before_planmemory.mlir)。这是两版使用的同一份 MaxParallel 输入，包含入口函数及所有 outlined VF 定义；入口函数从 **368 行**开始。下文 SSA 均指入口函数内的值。

| 项目 | stable | current |
|---|---|---|
| 编译通过策略 | PlanMemory 九次 attempt 均溢出；外层切换 VF Fusion 为 AllOp 后通过 | PlanMemory 第一档，通过多级 MultiSpec 地址规划 |
| multibuffer | 保留 | 保留 |
| 原始策略的 UB 地址上界 | 未找到可行布局 | 253952 B（248 KiB） |
| 原两轮 kernel 均值（已核对原始样本） | 46.5304 µs | 48.1981 µs |

### 性能复核结论（2026-10-20）

**1. 原始结论：统计正确，但不能据此认定 current 稳定慢 3.58%。** 原两轮均值为 stable `46.5304 µs`、current `48.1981 µs`；按原测试复验四轮后，差距从 `1.6677 µs` 缩小到 `0.2843 µs`，原差距未稳定复现。

**2. 复验结论：默认策略下，两版性能接近。** 同一进程、相同输入，直接交错执行 backward kernel 共 12 轮，每组统计 240 次：

| 编译版本 / VF Fusion 策略 | kernel 均值 |
|---|---:|
| stable / 回退 AllOp | 41.0143 µs |
| current / MaxParallel | 41.1387 µs |
| current / 强制 AllOp | 39.5678 µs |

current 默认仅慢 `0.1244 µs（0.30%）`。此处为单 kernel 测量，绝对耗时不与原测试混比；各组梯度检查均通过。

**3. VF Fusion 的影响：本例切到 AllOp 会加速。** 固定 current，MaxParallel → AllOp 后快 **1.5709 µs（3.82%）**，12 轮均同向。AllOp 将归约及后续计算融合，减少中间结果跨 VF 写回、重读 UB；MaxParallel 不保证更快。固定 AllOp 时，current 又比 stable 快 **1.4465 µs（3.53%）**。因此，本例默认 MaxParallel 的性能代价抵消了 current 在相同 AllOp 策略下的收益。

详细实验与 IR：[gated_vffusion_20261020](/home/m00953828/mojo/Q3_triton_kernel/runs/gated_vffusion_20261020)。

其中 `%alloc_43` 的有效区域通过 `hivm.hir.copy` 写入 `%alloc_45`（IR 474–479 行）；`%alloc_45` 随后被 op 118、146、149 的 VF 读取。`%alloc_69` 在 op 149 写入，op 152 经 `%subview_70` 执行 `hivm.hir.store`（IR 517–519 行）。

### stable 为什么九次都没有成功

| attempt | 内部策略 | 本例实际效果 |
|---|---|---|
| 1–3 | 原始策略 | 保留 multibuffer、VF reachable check；改变 shuffle seed |
| 4–6 | 第二档：尝试 remove multibuffer | **没有移除**：代码要求同时存在 AIC/AIV 的 CV 模块，本例是纯 AIV；仍保留 11 处标记 |
| 7–9 | 第三档：关闭 VF reachable check | 放宽可选 inplace 候选，仍保留 multibuffer |

九次不改变 VF 划分。贪心 inplace 都把 `%alloc_69` 合并到 op 149 的一个输入，只有三类结果：

| attempt | 合并后的 SSA 组 | 合并后生命周期 | 合并后容量 |
|---|---|---|---|
| 1、6、7、8、9 | `%alloc_69` + `%alloc_45` | `[110,152]` | 2×16 KiB |
| 2、3 | `%alloc_69` + `%alloc_42` | `[106,152]` | 2×16 KiB |
| 4、5 | `%alloc_69` + `%alloc_66` + `%alloc_49` | `[118,152]` | 2×16 KiB |

这里要区分**单份大小**与**multibuffer 份数**：`%alloc_69` 和 `%alloc_45` 的类型都是 `memref<4x1024xf32>`，单份均为 **16 KiB**；区别是 `%alloc_69` 标记了 `hivm.multi_buffer = 2`（IR 515 行），需要两份。stable 的 `GenerateInplaceList` 比较单份 `constBits`，要求被复用输入大小 ≥ 输出大小，本例为 `16 KiB ≥ 16 KiB`，满足条件（源码 1415–1418 行）。

规划顺序是：**先合并逻辑 StorageEntry，再展开 multibuffer，最后分配地址**。`MergeInplaceSE` 将合并组的 `multiBufferNum` 设为 `max(1,2)=2`（1586–1588 行），随后 `ExpandMultiBufferStorageEntry` 为该组展开两份 16 KiB 并统一规划地址（1603–1609 行）。因此这里不是让 32 KiB 输出塞进一个已分配的 16 KiB 地址块，而是两者共享一个最终按 **2×16 KiB** 规划的组。

例如 attempt 1：`%alloc_45` 原为 **16 KiB、`[110,149]`**，`%alloc_69` 原为 **2×16 KiB、`[149,152]`**；合并后变成 **2×16 KiB、`[110,152]`**。它虽然减少了总分配量，却增加了前一阶段的地址占用。

同时，原分配顺序较晚才处理 `%alloc_7` + `%alloc_64` 这个跨循环的必需合并组（生命周期 `[43,169]`）。九次最终均在该组的 16 KiB 分配处失败：起始地址 `295040 B`，末端 `311424 B`，超过 UB 上限 `253952 B`。换 seed、放宽 reachable check 均未得到可行布局；第二档又没有实际移除 multibuffer。

### current 在哪一层策略成功

**第一档 policy 成功**：保留全部 11 处 multibuffer 标记、VF reachable check 开启；使用固定输入、局部 inplace 选择和 DSATUR 排序。内部先试 `no pipe stall`（单级 level 3），超限；随后 `multi level plan strategy`（MultiSpec 允许 level 3→0）通过，最终上界 **248 KiB**，校验 39 个 StorageEntry。

op 149 的三个 inplace 候选均不选（`candidates=3 selected=0`），因此 `%alloc_69` 保持 `[149,152]` 的短生命周期。最终地址如下；`+` 表示合并到同一个 StorageEntry 的 SSA。

| SSA / StorageEntry 组 | 生命周期 | current 地址（KiB，左闭右开） |
|---|---|---|
| `%alloc_28`，两份缓冲 | `[72,118]` | `[32,48)`、`[48,64)` |
| `%alloc_69`，两份缓冲 | `[149,152]` | **`[32,48)`、`[48,64)`，复用 `%alloc_28` 的地址** |
| `%alloc_45`，一份缓冲 | `[110,149]` | `[208,224)` |
| `%alloc_7` + `%alloc_64` | `[43,169]` | `[128,144)` |
| `%alloc_9` + `%alloc_65` | `[46,169]` | `[144,160)` |

矩形横向表示生命周期，纵向表示地址范围；红虚线是 **248 KiB UB 上限**，灰色为其余 StorageEntry。上图取 stable attempt 1；另外两类合并见上表。图按规划日志绘制，不表示硬件同时执行的快照。

看图重点：stable 的橙色合并组从 op 110 起占两份缓冲，红色的 `%alloc_7` + `%alloc_64` 组最终被放到 UB 上限之外；current 将 `%alloc_69` 单独保留，并放入 `%alloc_28` 已结束使用的同一地址范围。stable 的 `311424 B` 只是失败布局末端，current 已证明 248 KiB 存在可行布局。

为区分 inplace 与排序的作用，在 current 独立诊断版中固定相同输入、seed=0、仅运行第一档，做两因素消融：

| inplace 选择 | 原分配顺序 | DSATUR 顺序 |
|---|---|---|
| 贪心合并 | UB overflow | UB overflow |
| 新局部选择 | UB overflow | **通过，248 KiB** |

诊断基线输出与正式 current 逐字节一致。**本例需要局部 inplace 选择与 DSATUR 排序配合：避免 `%alloc_69` 与早期输入的不利合并，再改善长生命周期组的放置顺序。**

stable 九次失败后，外层 `bishengir-compile` 捕获 `ub overflow`，将 VF Fusion 从 MaxParallel 切到 AllOp、tuning delta 增加 2，再从 HIR pipeline 起点重跑并通过。这个外层重试才改变 VF 划分，与 PlanMemory 内部第二档不同。

## 3. Jagged softmax backward：两轮约快 2.86%

Kernel：`jagged_softmax_backward_kernel`。`B=8, H=512, max_seq_len=2048`，实际输入 `8789×512`、FP16；`BLOCK_SIZE_N=32, multibuffer=True`。

| 项目 | stable | current |
|---|---:|---:|
| 第 1 轮 | 198.2612 µs | 192.6376 µs |
| 第 2 轮 | 198.3462 µs | 192.6304 µs |
| 两轮均值 | 198.3037 µs | 192.6340 µs |
| UB 地址上界 | 235520 B | 235520 B |

特点：先归约 `dy*y`，再重新加载并计算梯度；两遍间保留小统计量，阶段性大 buffer 可以复用。

**两轮同向，平均减少 5.670 µs（2.86%），暂列加速候选。** 容量没有下降，尚未通过同步 IR 和单变量实验确认加速原因。
